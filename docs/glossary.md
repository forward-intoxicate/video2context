# 领域词表：修同音词与专有名词

中文语音识别最难的一类错误是**同音词**：声学上完全一样，模型只能靠语言知识猜。
典型例子（来自 `samples/formula.mp4` 一节导数课）：

| 音频里说的是 | 识别成了 | 类型 |
|---|---|---|
| `u(x)` | `右F4` | 拉丁字母被听成同音汉字 |
| `v(x)` | `位F4` | 同上 |
| `x0` | `F0` | 同上 |
| `导数` | `倒数` | 中文同音歧义 |
| `再求导` | `在求导` | 中文同音字 |

本功能让识别结果在这些位置变正确。**实测 `右/位` 错误从 13~14 处降到 0 处。**

---

## 一、三种用法

### 1. 手写词表（完全离线，最可控）

```powershell
# terms.txt 内容示例：
#   右F4 -> u(x)      「错形 -> 正确」表示还原
#   位F4 -> v(x)
#   x0
#   可导
python -m video2context 视频.mp4 --glossary terms.txt
```

一行一个；带 `->`（或 `=>`、`→`）的按"还原"处理，其余视为普通术语。

### 2. 自动两遍解码（推荐先跑 dry-run）

```powershell
# 第一步：只生成词表，看一眼对不对（不做正式转写）
python -m video2context 视频.mp4 --dry-run-glossary --glossary-out terms.json

# 第二步：确认后带着词表正式转写（完全离线，不再调用大模型）
python -m video2context 视频.mp4 --glossary terms.json

# 或者一条命令跑完（自动推断 + 正式转写）
python -m video2context 视频.mp4 --auto-glossary
```

需要先配好大模型密钥（见 [README「领域词表」](../README.md#领域词表修同音词专有名词)）：
`V2C_LLM_API_KEY` 环境变量或工程根目录的 `.env` 文件。

### 3. 作为库调用

```python
from video2context import Glossary, SymbolRepair, process, scan_and_build_glossary, TranscribeOptions

glossary = scan_and_build_glossary("视频.mp4", TranscribeOptions(scan_duration=90))
print(glossary.describe())
result = process("视频.mp4", TranscribeOptions(glossary=glossary, formats=("json", "srt")))
```

## 二、自动模式怎么跑的

```
① 采样        取音频前 90 秒（--scan-duration 可调）
② 粗转写      同一个模型 + 无提示词 + 关掉上文条件   →  右F4和位F4如果在F0处可倒…
③ LLM 推断    粗转写 → {"domain": "数学分析，导数运算",
                        "symbols": [["右F4","u(x)"], ["位F4","v(x)"], ["F0","x0"]]}
④ 拼提示词    → "数学分析，导数运算。符号：u(x)、v(x)、x0。"（20~40 字）
⑤ 正式转写    带这个词表重跑全片
⑥ 验证回退    期望符号命中 0 次 → 判定偏置失效 → 自动回退到无词表结果
```

几个刻意的设计决定，都由实测数据支撑：

| 决定 | 原因 |
|---|---|
| **第一遍只用采样**（默认 90 秒） | 领域词汇在开头就出现了。1 小时视频的第一遍开销只有 3~5 秒（**+5% 以内**，而不是"成本翻倍"） |
| **第一遍用同一个模型** | 避免加载第二个模型 —— 8GB 显存机器上"先小模型再大模型"会因内存碎片直接 OOM（实测踩过） |
| **第一遍关掉 `condition_on_previous_text`** | 第一遍必然有错，开着会把错误自我强化（实测 13 错 vs 8 错） |
| **只保留 `symbols`，丢掉术语列表** | 见下面「LLM 输出的陷阱」——术语列表会把错别字喂回来 |
| **提示词压到 40 字以内** | 只放还原后的符号；实测这一形态最稳定 |
| **必须验证并回退** | 偏置会**静默失效**（见下） |

## 三、实测结论（这些是实验数据，不是推测）

测试素材：`samples/formula.mp4`（72 秒，导数运算法则中文课），模型 `large-v3`。

### 3.1 LLM 确实能还原符号 —— 不用给例子

指令只写"可能把拉丁字母或数学符号听成了汉字"，**不给任何示例**，DeepSeek 的真实返回：

```json
{"domain": "数学分析，导数运算",
 "symbols": [["右F4","u(x)"], ["位F4","v(x)"], ["F0","x0"], ["右加位","u+v"]]}
```

完全正确。加示例、要求分步推理也都正确 —— 所以这一步是可靠的。

### 3.2 陷阱：让 LLM 输出"术语列表"会把错别字带回来

同一个返回里如果还要它给 `glossary`（术语数组），它会填：

```json
"glossary": ["右F4", "位F4", "F0", "可导", ..., "先求岛", "再降降"]
```

把**错别字当成术语**抄了进来。直接拼进 prompt 后：

| prompt 内容 | `u/v` 正确 | `右/位` 错误 |
|---|---|---|
| 含正确符号 `u(x)、v(x)、x0、u+v` | **13** | **0** |
| 含错别字 `右F4、位F4` | 0 | **13**（比不加提示词还差） |

**所以本工程的 LLM schema 只要 `symbols`（"错形 → 正确"的还原对），不要术语列表。**

### 3.3 最重要的发现：Whisper 的提示词偏置会**静默失效**

同样包含正确符号 `u(x)、v(x)、x0、u+v` 的 prompt，措辞微调后结果天差地别，**且完全确定性复现**（同一 prompt 跑 3 次结果一字不差）：

| prompt 变体 | token 数 | 结果 |
|---|---|---|
| 极简 `u(x) v(x) x0 u+v` | 16 | ✅ 13/0 |
| 长词表（无填充词） | 85 | ✅ 13/0 |
| **含正确符号的长 prompt A** | 92 | ❌ **0/13**（复现 3 次） |
| **含正确符号的长 prompt B** | 97 | ❌ **0/13** |
| 最长的一个（114 token） | 114 | ✅ 13/0 |
| 只有裸字母 `u v x0` | 7 | ❌ 0/13 |

我提出四个假设去解释失败，**全部被实验否定**：

| 假设 | 反例 | 结论 |
|---|---|---|
| 填充词有害 | 含"带进去、公式、再加"的变体**成功** | ❌ |
| prompt 太长 | 114 token 的变体**成功** | ❌ |
| token 截断（上限 223） | 所有变体都远低于上限 | ❌ |
| 裸字母有害 | 含裸 `u、v` 的变体**成功** | ❌ |

**结论：无法事先预测哪种措辞会失效。** 因此工程上不能盲目信任词表 —— 必须带**验证 + 回退**。

### 3.4 验证机制

带词表转写完成后，用 :func:`video2context.symbol_hit_score` 统计四个量：

| 字段 | 含义 |
|---|---|
| `expected_hits` | 还原出的正确符号在结果里出现的总次数（如 `u`、`v`、`x0`） |
| `hit_probes` / `coverage` | 有几个**不同的**符号出现过 / 占比 —— 比总次数更能反映真实情况 |
| `wrong_hits` | 词表里给出的**错误写法**在结果里残留了几次 |
| `unresolved` | 仍然残留的错误写法清单，如 `["位F4→v(x)"]` |

**判断规则（基于证据，而不是猜词有没有出现）**：

* 正确符号**一个都没命中**，且**仍有错误写法残留** → 判定偏置完全失效 → **自动回退**到无词表版本重跑
* 部分命中、部分仍有残留 → 保留结果，但日志提醒你
* 某个词压根没在音频里出现（不算失败，也不回退）

回退只在"完全失效"时发生，所以正常情况下**不会**多付一次转写成本。校验结果写进 JSON：

```json
"glossary": {
  "source": "llm",
  "domain": "数学分析，导数运算",
  "symbols": [{"from": "右F4", "to": "u(x)"}],
  "prompt": "数学分析，导数运算。符号：u(x)、v(x)、x0。",
  "scan": {"duration": 90.0, "model": "large-v3", "chars": 214},
  "llm": {"model": "deepseek-chat", "prompt_tokens": 194, "completion_tokens": 176},
  "verification": {
    "expected_hits": 10, "wrong_hits": 0,
    "probes": ["u", "v", "x0"], "hit_probes": ["u", "v"],
    "missing_probes": ["x0"], "unresolved": [],
    "coverage": 0.667, "fallback_used": false
  }
}
```

#### ⚠️ 校验的局限（实测踩到）

`wrong_hits` 只匹配**词表里给出的确切错误写法**。如果词表里记的是 `位F4`，而模型这次只写了 `位`（没有 `F4` 后缀），就统计不到 —— 上面的真实例子就是这样：
`v` 在 `vx` 处修好了（`hit_probes` 里有 `v`），但同一份结果里 `u加位` 还是错的，而 `wrong_hits` 显示 0。

**所以判断效果时请同时看 `coverage` 和实际文本**，不要只看 `wrong_hits`。

#### 模型大小的影响（实测）

同一个词表，`large-v3` 与 `small` 的效果差别明显：

| 模型 | 结果 |
|---|---|
| `large-v3` + 词表 | `u`、`v`、`x0` **全部修正**（`右/位` 错误 13 → 0） |
| `small` + 词表 | 只有 `u` 较好、`v` 时对时错、`x0` 仍错（小模型本身能力有限） |

**结论：词表在 `large-v3` 上收益最大；小模型不要指望词表救回来。**

## 四、成本

| 项 | 实测 |
|---|---|
| 第一遍（采样 90 秒，large-v3） | 约 3~5 秒 GPU |
| 大模型调用 | 约 200~400 token（DeepSeek 约 **0.0003 元**） |
| 第二遍 | 与普通转写相同 |

手写词表模式则是**零额外开销、零联网**。

## 五、局限与注意事项

1. **偏置可能失效**（3.3 节）。本工程用"验证 + 回退"兜底，但**不会**保证一定改善。
2. **LLM 可能猜错符号**，错误一旦被当成提示词就会铺满全片。所以推荐 `--dry-run-glossary` 先看一眼，再正式跑。有课件 OCR 的话应以 OCR 为准（那是事实，LLM 的推断只是猜测）。
3. **只解决"已知词汇"**。视频里第一次出现、且上下文无线索的人名，任何方案都只能猜。
4. **口语公式 ≠ 排版公式**。ASR 只能得到"u 加 v 的导数"这种**读法**，要得到 `(u+v)'=u'+v'` 这种**排版**需要另一条路：视频关键帧 + 数学 OCR。
5. **长音频**：`condition_on_previous_text` 能显著提升词表偏置的持续性，但在很长的音频上可能陷入重复。建议长视频配合 `--duration` 分段跑，每段都带词表。

## 六、密钥安全

* 密钥只从 `V2C_LLM_API_KEY` 环境变量或工程根目录的 `.env` 读取，**没有任何命令行参数可以传密钥**（命令行参数会进进程列表和命令历史）。
* `.env` 已在 `.gitignore` 中；仓库里只有 `.env.example` 模板。
* `python -m video2context doctor` 会用 `sk-***abcd` 的形式显示配置状态，**不打印明文**。
* 报错信息、日志、JSON 里出现的密钥都会被 :func:`video2context.config.redact` 打码。
* 提交前跑一次 `python scripts/check_secrets.py`（CI 里也会自动跑）。
